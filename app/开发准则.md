## 一、核心原则

> **引擎只做编排，不做实现。每个功能一个模块，每个模块一个文件。**

`engine.ts` 的角色是**调度中心**（Orchestrator），不是**万能口袋**（God Object）。它的职责仅限于：

1. 实例化各功能模块
2. 在主循环中按顺序调用模块的 `update()` / `render()` 方法
3. 处理模块通过回调上报的副作用（粒子、音效、振动、UI 通知等）
4. 管理游戏状态机（MENU → PLAYING → PAUSED → GAME_OVER 等）

**禁止**在 `engine.ts` 中直接编写新功能的业务逻辑。

## 三、模块开发模式

### 模式 A：实例模块（有状态模块）

**适用场景**：需要维护自身状态的功能（计时器、冷却、阶段切换等）。

**模板结构**：

```typescript
/**
 * @fileoverview [功能名称]模块
 * @description [一句话描述模块职责]
 */

import { /* 需要的类型 */ } from '../../types';

// ========== Config 接口 ==========
/** 模块配置：从引擎读取的只读/可读数据 */
export interface XxxSystemConfig {
  /** 画布宽度 */
  canvasWidth: number;
  /** 防御线 Y 坐标（用 getter 函数保证实时性） */
  defenseLineY: () => number;
  // ... 其他配置
}

// ========== Callbacks 接口 ==========
/** 模块回调：向引擎上报副作用 */
export interface XxxSystemCallbacks {
  /** 添加浮动文字 */
  onAddFloatingText?: (x: number, y: number, text: string, color: string) => void;
  /** 播放音效 */
  onPlaySound?: (name: string) => void;
  /** 屏幕震动 */
  onScreenShake?: (amount: number) => void;
  /** 添加粒子 */
  onAddParticle?: (particle: any) => void;
  /** 更新经济 */
  onEconomyUpdate?: (economy: any) => void;
  /** 更新防线 */
  onDefenseUpdate?: (hp: number, maxHp: number) => void;
  // ... 其他回调
}

// ========== 模块类 ==========
export class XxxSystem {
  private config: XxxSystemConfig;
  private callbacks: XxxSystemCallbacks;

  constructor(config: XxxSystemConfig, callbacks: XxxSystemCallbacks) {
    this.config = config;
    this.callbacks = callbacks;
    // 初始化内部状态
  }

  /** 每帧更新 */
  update(dt: number, time: number): void {
    // 核心逻辑
  }

  /** 重置状态 */
  reset(): void {
    // 清理状态
  }
}
```

**在 engine.ts 中的集成方式**：

```typescript
// 1. 构造函数中实例化
this.xxxSystem = new XxxSystem(
  {
    canvasWidth: this.canvas.width,
    defenseLineY: () => this.defenseLineY,
  },
  {
    onAddFloatingText: (x, y, text, color) => { this.addFloatingText(x, y, text, color); },
    onPlaySound: (name) => { this.audio.play(name); },
    onScreenShake: (amount) => { this.screenShake = amount; },
  }
);

// 2. update() 主循环中调用
this.xxxSystem.update(this.dt, this.time);

// 3. resetGame() 中重置
this.xxxSystem.reset();
```

### 模式 B：静态渲染模块（无状态模块）

**适用场景**：纯渲染逻辑，不维护状态，通过参数接收所有数据。

**模板结构**：

```typescript
/**
 * @fileoverview [渲染功能名称]渲染模块
 * @description [一句话描述]
 */

// ========== Config 接口 ==========
export interface XxxRenderConfig {
  /** 需要渲染的数据 */
  data: SomeType[];
  /** 图片资源 */
  images: Record<string, HTMLImageElement>;
  /** 时间戳 */
  time: number;
  // ... 其他参数
}

// ========== 静态方法 ==========
export class XxxRenderer {
  /**
   * 渲染 [功能名称]
   * @param config - 渲染配置
   * @param ctx - 画布上下文
   */
  static render(config: XxxRenderConfig, ctx: CanvasRenderingContext2D): void {
    // 纯渲染逻辑，不修改任何状态
  }
}
```

**在 engine.ts 中的集成方式**：

```typescript
// render() 方法中直接调用静态方法
XxxRenderer.render(
  {
    data: this.xxxData,
    images: this.images,
    time: this.time,
  },
  this.ctx
);
```

## 四、开发流程

### 4.1 新功能开发步骤

```
步骤 1 ──→ 步骤 2 ──→ 步骤 3 ──→ 步骤 4 ──→ 步骤 5 ──→ 步骤 6
分析需求   创建模块   定义接口   实现逻辑   集成到引擎  验证
```

| 步骤 | 操作 | 产出 |
|:---:|------|------|
| 1 | **分析需求**：确定功能属于哪种模块类型（实例 / 静态） | 设计决策 |
| 2 | **创建模块文件**：在 `engine/` 下创建子目录和文件 | `engine/xxx/XxxSystem.ts` |
| 3 | **定义接口**：Config 接口（入参）+ Callbacks 接口（出参） | 两个 interface |
| 4 | **实现逻辑**：编写模块核心代码，通过 `this.callbacks` 上报副作用 | 完整模块代码 |
| 5 | **集成到引擎**：在 `engine.ts` 构造函数中实例化，在 `update()`/`render()` 中调用 | 3 处引擎修改 |
| 6 | **验证**：`npx tsc --noEmit` + `npx vite build` 必须通过 | 编译 + 构建成功 |

### 4.2 引擎修改清单

每次新增模块，只需在 `engine.ts` 中修改 **3 个位置**：

| 位置 | 操作 | 代码量 |
|------|------|:---:|
| 构造函数 | `new XxxSystem(config, callbacks)` | ~15 行 |
| `update()` | `this.xxxSystem.update(dt, time)` | 1 行 |
| `resetGame()` | `this.xxxSystem.reset()` | 1 行 |

如果是静态渲染模块，只需在 `render()` 中加 1 行调用。

## 五、回调接口规范

### 5.1 标准回调命名

所有回调统一使用 `on` 前缀，动词后置：

```typescript
// ✅ 正确
onAddFloatingText    // 添加浮动文字
onPlaySound          // 播放音效
onScreenShake        // 屏幕震动
onEconomyUpdate      // 更新经济
onDefenseUpdate      // 更新防线
onPlayerUpdate       // 更新玩家
onStateChange        // 切换状态
onSpawnParticle      // 生成粒子

// ❌ 错误
addFloatingText      // 缺少 on 前缀
handleFloatingText   // 不明确
onFloatingTextAdd    // 动词后置不符合习惯
```

### 5.2 回调设计原则

1. **回调必须可选**（`?:`）：模块不应假设回调一定存在，调用前检查 `this.callbacks.xxx?.()`
2. **回调不应包含业务逻辑**：回调只负责通知引擎，具体处理由引擎完成
3. **避免回调地狱**：每个模块的回调数量控制在 5-15 个以内
4. **箭头函数包装**：在引擎中注入回调时，如需访问运行时状态，必须用箭头函数包装

```typescript
// ✅ 正确：箭头函数包装，运行时动态读取
onGetRoaches: () => this.roaches

// ❌ 错误：直接引用，捕获构造时的值
onGetRoaches: this.roaches
```

### 5.3 数据传递方向

```
引擎 ──Config接口──→ 模块（读取数据）
引擎 ←──Callbacks── 模块（上报副作用）
```

- **Config**：引擎 → 模块，传递模块需要读取的数据
- **Callbacks**：模块 → 引擎，模块通知引擎执行副作用

## 六、代码规范

### 6.1 文件组织

```
engine/xxx/
├── XxxSystem.ts        # 实例模块（有状态逻辑）
└── XxxRenderer.ts      # 静态渲染模块（如有渲染需求）
```

### 6.2 注释规范

每个模块文件必须包含：

```typescript
/**
 * @fileoverview [功能名称]模块
 * @description [一句话描述模块职责]
 */
```

每个公开方法必须包含 JSDoc：

```typescript
/**
 * 更新风扇状态：递减计时器、更新叶片角度、对范围内蟑螂施加减速/击退
 * @param dt - 帧间隔时间（秒）
 * @param roaches - 当前所有蟑螂列表
 */
update(dt: number, roaches: Roach[]): void { ... }
```

### 6.3 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 模块类 | `XxxSystem`（实例）/ `XxxRenderer`（静态） | `FanSystem`、`RoachRenderer` |
| Config 接口 | `XxxSystemConfig` / `XxxRenderConfig` | `FanSystemConfig` |
| Callbacks 接口 | `XxxSystemCallbacks` | `BossBattleCallbacks` |
| 私有属性 | `private` 前缀 | `private config: FanSystemConfig` |
| 回调方法 | `on` + 动词 + 名词 | `onAddFloatingText` |

## 七、反面案例

### ❌ 错误做法：直接在 engine.ts 中写功能

```typescript
// ❌ 不要这样做！
update() {
  // 直接在 engine.ts 中写风扇逻辑
  if (this.fanActive) {
    this.fanTimer -= dt;
    if (this.fanTimer <= 0) {
      this.fanActive = false;
      this.fanTimer = 0;
    }
    // 风扇效果：减速蟑螂
    for (const roach of this.roaches) {
      if (roach.x > fanX - fanRadius && roach.x < fanX + fanRadius) {
        roach.speed *= 0.5;
      }
    }
  }
  // ... 更多功能直接堆在这里
}
```

**问题**：`engine.ts` 会不断膨胀，最终回到 9700 行的噩梦。

### ✅ 正确做法：提取为独立模块

```typescript
// ✅ engine.ts 中只需一行
this.fanSystem.update(dt, this.roaches);

// ✅ 所有逻辑在 FanSystem.ts 中
```

## 八、代码审查清单

提交代码前，逐项检查：

- [ ] 新功能代码在独立模块文件中，不在 `engine.ts` 中
- [ ] 模块通过 Config 接口接收数据，通过 Callbacks 接口上报副作用
- [ ] 所有回调使用 `?.()` 可选调用，防止空引用
- [ ] 引擎中注入回调时使用箭头函数包装（如需要运行时状态）
- [ ] 模块提供 `reset()` 方法（如有状态），并在 `engine.ts` 的 `resetGame()` 中调用
- [ ] `reset()` 方法仅重置单局数据，不重置持久化数据（如成就解锁状态、天赋进度等）
- [ ] `updateConfig()` 方法支持动态更新配置（如需要）
- [ ] 所有公开方法有 JSDoc 注释
- [ ] `index.ts` 中导出新模块
- [ ] `npx tsc --noEmit` 零错误
- [ ] `npx vite build` 构建成功
- [ ] 更新 `引擎迁移.md` 变更记录
- [ ] ID 生成通过回调注入（禁止模块级独立计数器，见二十）
- [ ] fireZones 清理使用 `filter` 保留持久火焰区域（`maxLife ≥ 1`），而非全量清空（见二十一）
- [ ] 图片加载使用 `Promise.all` 等待所有图片、添加 `onerror` 处理（见二十二）
- [ ] 递归方法中 `depth` 计数器正确配对（`++`/`--`），防止死循环或指数爆炸（见二十三）
- [ ] 临时武器弹药使用整数递减（`-= 1`），而非浮点递减（见二十四）
- [ ] 方法名准确反映职责，不包含已过时的功能描述（见二十五）
- [ ] 已移除的子系统代码和注释彻底清理，不留 `[REMOVED]` 标记（见二十五）

## 十、数值系统调用规则

> **核心原则：关卡内金币与总金币分离，所有奖励通过 `pendingRewards` 流转，仅在胜利时结算。**

### 10.1 金币体系架构

```
                    关卡内获得（HUD 实时显示）
                    ═══════════════════════════
    击杀蟑螂 ──→ pendingRewards ──→ GameHUD 显示 ¥{pendingRewards}
    成就奖励 ──→ onAddPendingReward()
    其他奖励 ──→ onAddPendingReward()
                    │
                    │ 关卡胜利时（gameVictory）
                    ▼
              victoryGoldReward ──→ 结算界面动画 ──→ settleVictoryGold()
                    │                                      │
                    │                                      ▼
                    │                              economy.money（总金币池）
                    │                              totalMoneyEarned（累计获得）
                    │
                    │ 关卡失败/退出
                    ▼
              pendingRewards = 0（金币不发放）
              economy.money 保持不变（已有金币池保留）
```

### 10.2 关键属性

| 属性 | 位置 | 类型 | 说明 |
|------|------|:---:|------|
| `pendingRewards` | `engine.ts` | `number` | 关卡内累计金币，HUD 实时显示，初始 0 |
| `victoryGoldReward` | `engine.ts` | `number` | 胜利时从 `pendingRewards` 拷贝，供结算界面动画展示 |
| `economy.money` | `Economy` 接口 | `number` | 总金币池（跨关卡持久化），初始值 = `menuShopMoney` |
| `economy.totalMoneyEarned` | `Economy` 接口 | `number` | 累计获得金币（含已花费），用于成就统计 |
| `menuShopMoney` | `GameCanvas.tsx` | `number` | React 状态，持久化到 `localStorage`，商店扣款用 |

### 10.3 模块中如何添加金币奖励

**✅ 正确做法：使用 `onAddPendingReward` 回调**

```typescript
// 在模块的 Callbacks 接口中定义
export interface XxxSystemCallbacks {

// 在模块中调用
```

**在 engine.ts 中绑定回调**：

### 10.4 金币结算流程

| 时机 | 触发 | 行为 |
|------|------|------|
| 关卡胜利 | `gameVictory()` → `settleVictoryGold()` | `pendingRewards` → `victoryGoldReward` → 结算界面动画 → `economy.money += victoryGoldReward` |
| 关卡失败 | `gameDefeat()` / `checkDefense()` | `pendingRewards = 0`，`economy.money` 保持不变（已有金币池保留） |
| 暂停退出 | `handleQuit()` | 同步 `engine.economy.money` 到 `menuShopMoney`（保留已有金币） |
| 新游戏/重新开始 | `resetGame()` | `pendingRewards = 0`，`victoryGoldReward = 0` |
| 购买消耗品 | `ConsumableSystem` | 扣减 `economy.money`（总金币池），不影响 `pendingRewards` |

### 10.5 引用同步检查清单

当 `resetGame()` 中创建新对象时，必须检查所有持有该对象引用的子系统：

```typescript
// engine.ts - resetGame()

this.roaches = [];
this.placedBombs = [];
this.deadTimedBombs = [];

// ② 必须同步到所有持有引用的子系统！
this.roachAISystem?.updateConfig({
  economy: this.economy,       // ← 必须同步
  player: this.player,         // ← 必须同步
  roaches: this.roaches,       // ← 必须同步
  placedBombs: this.placedBombs,     // ← 必须同步
  deadTimedBombs: this.deadTimedBombs, // ← 必须同步
});
```

**检查项**：
- [ ] `resetGame()` 中创建的新数组/对象是否已同步到所有持有引用的子系统
- [ ] 使用 getter 函数（`getEconomy: () => this.economy`）的子系统不受影响
- [ ] 使用固定引用（`economy: this.economy`）的子系统必须通过 `updateConfig()` 同步

### 10.6 经济数值的来源

所有游戏内经济数值必须通过 `EconomyManager` 统一计算，禁止在模块中硬编码：

## 十一、浮动文字调用规则

> **核心原则：所有浮动文字内容、颜色、字体、大小必须集中管理，禁止硬编码。颜色已内联到每个 `TEXT_CONFIG.combat` 条目中（`{ text, color }` 格式），与文字内容统一管理。**

## 十二、音效系统调用规则

> **核心原则：AudioManager 统一管理所有音效，通过 Web Audio API 合成 + HTMLAudioElement 播放两种方式实现。**

### 12.1 音效系统架构

```
游戏逻辑层（模块/引擎）
    │
    │ 调用 this.audio.xxx()
    ▼
AudioManager（audio.ts）
    ├── HTMLAudioElement（文件音效）
    │   ├── BGM: bgm, gameOverBgm, victoryBgm
    │   ├── SFX: fireSfx, killSfx, swatterSfx, reloadSfx, clickSfx
    │   └── 一次性: nurse_cast.mp3, mutant_transform.mp3, flying_dodge.mp3
    │
    └── Web Audio API（合成音效）
        ├── 短促音效: playCoinTick, playCountdownTick, playBreachSound, playDanmaku
        ├── 琶音序列: playItemDrop, playItemDropFanfare, playStickySpray
        ├── Boss 音效: playBossCharge, playBossChargeHit
        └── 循环音效: startFanLoop/stopFanLoop, startFireWallBurn/stopFireWallBurn, startFlyingBuzzLoop/stopFlyingBuzzLoop
```

### 12.2 BGM 管理规则

**BGM 生命周期**：切换 → 播放 → 停止，三者严格分离。

```
场景切换时              战斗开始时              游戏结束时
switchBGMForScene() → startLevelBGM() → stopBGM()
（不播放）              （播放）                （停止）
```

| 方法 | 调用时机 | 说明 |
|------|------|------|
| `switchBGMForScene(scene, difficulty)` | 关卡开始前（`start()` 之前） | 根据场景/难度选择 BGM 路径，调用 `switchBGM()` 创建新 Audio 元素，**不播放** |
| `startLevelBGM()` | 3-2-1 倒计时结束后 | 播放当前 BGM |
| `stopBGM()` | 关卡结束/失败/退出 | pause + currentTime = 0 |
| `pauseBGM()` / `resumeBGM()` | 暂停/恢复 | 暂停菜单 |
| `fadeOutBGM(targetVol, duration)` | Boss 战/商店场景 | 渐变淡出到指定音量 |
| `playGameOverBGM()` | 防线被突破 | 每次重新创建 Audio 元素确保可靠播放 |
| `stopGameOverBGM()` | 退出结算界面 | 停止并清理 |
| `playVictoryBGM()` | 关卡胜利 | 播放胜利 BGM |
| `stopVictoryBGM()` | 退出胜利界面 | 停止胜利 BGM |

**关键约束**：

1. **创建顺序**：`new Audio()` → 设置 `preload = 'auto'` → 设置 `src`（不可颠倒）
2. **切换前必须先停止旧 BGM**：`pause()` → `currentTime = 0` → `removeAttribute('src')`（不要用 `load()` 避免触发 error 事件）
3. **`switchBGM()` 必须设置 `muted`**：`this.bgm.muted = this.isMuted`（不能硬编码 `false`）
4. **`play()` 必须处理 `AbortError`**：这是 `pause()` 打断 `play()` 的正常竞态，静默忽略
5. **主菜单无 BGM**：BGM 仅在关卡战斗期间播放（3-2-1 倒计时后）

### 12.3 SFX 播放规则

**文件音效**（HTMLAudioElement）：火焰、击杀、电蚊拍、换弹、点击

## 十三、React UI 组件与引擎通信规则

> **核心原则：引擎通过回调通知 React 状态变更，React 通过 ref 调用引擎方法，数据单向流动。**

### 13.1 通信架构

```
┌─────────────────────────────────────────────────┐
│  GameCanvas.tsx（桥接组件）                       │
│                                                  │
│  engineRef = useRef<GameEngine>()                │
│  ┌──────────────┐       ┌──────────────────────┐ │
│  │ engine.ts    │ 回调   │ React State          │ │
│  │              │──────→│ economy, player,      │ │
│  │ onEconomyUpd.│       │ pendingRewards,       │ │
│  │ onPendingRew.│       │ wave, defenseHp, ...  │ │
│  │ onStateChange│       └──────────┬───────────┘ │
│  │ ...          │                  │ props       │
│  └──────────────┘       ┌──────────▼───────────┐ │
│         ▲               │ 子组件                │ │
│         │ 方法调用       │ GameHUD              │ │
│         │               │ GameOverScreen       │ │
│  engineRef.current      │ PauseScreen          │ │
│  .start() / .stop()     │ ShopScreen           │ │
│  .restart() / .pause()  └──────────────────────┘ │
└─────────────────────────────────────────────────┘
```

### 13.2 核心状态同步模式

**引擎 → React 单向数据流**：

```typescript
// GameCanvas.tsx - 绑定回调
engine.onEconomyUpdate = (e: Economy) => setEconomy({ ...e });        // 展开新对象触发渲染
engine.onPendingRewardUpdate = (rewards: number) => setPendingRewards(rewards);
engine.onWaveUpdate = (w: number) => setWave(w);
engine.onDefenseUpdate = (hp: number, maxHp: number) => {
    setDefenseHp(hp);
    setMaxDefenseHp(maxHp);
};
engine.onStateChange = (state: GameState) => setGameState(state);
```

**关键原则**：
- 对象类型状态必须展开（`{ ...e }`）创建新引用，否则 React 不会重新渲染
- 引擎回调中不要做复杂计算，只做 `setState`
- 使用 `useCallback` 包装传递给子组件的回调，避免不必要的重渲染

### 13.3 GameOverScreen 结算界面

**Props 接口**：

| Prop | 类型 | 说明 |
|------|------|------|
| `economy` | `Economy` | 引擎经济状态（包含 `money` 总金币池） |
| `isVictory` | `boolean` | 胜利/失败 |
| `victoryGoldReward` | `number` | 关卡内获得的金币（用于动画展示） |
| `onSettleGold` | `() => void` | 动画完成后回调 → 调用 `engine.settleVictoryGold()` |
| `menuMoney` | `number` | 跨关卡总金币（`menuShopMoney`），失败时显示 |
| `audio` | `AudioManager` | 音效管理器（用于动画音效） |

**金币动画实现规则**：

```typescript
// 动态时长：基础 1000ms + 每金币 3ms，最低 800ms，最高 5000ms
const duration = Math.max(800, Math.min(1000 + reward * 3, 5000));
const tickInterval = 50; // 固定 50ms 间隔，音效保持固定节奏
const steps = Math.round(duration / tickInterval);

// 每步更新 displayGold + 播放音效
setDisplayGold(newGold);
audio?.playCoinTick();
```

**结算流程**：

```
胜利: gameVictory() → pendingRewards → victoryGoldReward
      → GameOverScreen 金币动画（1-5s，动态时长）
      → onSettleGold() → engine.settleVictoryGold()
      → economy.money += victoryGoldReward

失败: gameDefeat() → pendingRewards = 0
      → GameOverScreen 显示 economy.money（已有金币池保留）
      → menuMoney 同步（handleQuit 时）
```

### 13.4 GameHUD 关卡内 HUD

**关键状态**：

| 状态 | 来源 | 显示内容 |
|------|------|------|
| `pendingRewards` | `engine.onPendingRewardUpdate` | 关卡内金币 ¥{N} |
| `economy.money` | `engine.onEconomyUpdate` | 总金币池（商店扣款用） |
| `wave` | `engine.onWaveUpdate` | 当前波次 |
| `defenseHp / maxDefenseHp` | `engine.onDefenseUpdate` | 防线血量 |

**注意**：HUD 金币显示使用 `pendingRewards`（关卡内），不是 `economy.money`（总金币池）。

### 13.5 退出/重启流程

```typescript
// handleQuit: 暂停退出 → 同步 economy.money → 停止引擎
const handleQuit = useCallback(() => {
    engineRef.current?.audio.stopBGM();
    engineRef.current?.saveProgress();
    setMenuShopMoney(engine.economy.money);  // 同步总金币池
    localStorage.setItem('roach_blaster_menu_money', String(engine.economy.money));
    engineRef.current?.stop();
}, []);

// handleRestart: 重新开始 → 停止音频 → 引擎重启 → 切换 BGM → 引擎启动
const handleRestart = useCallback(() => {
    engineRef.current?.audio.stopBGM();
    engineRef.current?.audio.stopVictoryBGM();
    engineRef.current?.audio.stopGameOverBGM();
    engineRef.current?.restart();
    // 必须在 restart() 的 stop() 之后、start() 之前切换 BGM
    engine.audio.switchBGMForScene(engine.currentScene, engine.difficulty);
    engine.start(gameMode, currentScene, true);
}, []);
```

## 十五、道具/库存系统规则

> **核心原则：道具库存修改必须创建新数组引用，删除后必须通知 UI 更新，确保 React 状态正确同步。**

### 15.1 库存数据流

```
拾取道具 ──→ inventory.push(item) ──→ onInventoryUpdate(inventory) ──→ React setState
    │
使用道具 ──→ 数量递减 ──→ 数量为 0 时 filter 移除 ──→ onInventoryUpdate(inventory)
    │
    ▼
React 重新渲染道具栏图标
```

### 15.2 数组不可变原则

**React 状态更新依赖引用变化**，必须创建新数组而非修改原数组：

```typescript
// ✅ 正确：使用 filter 创建新数组引用
this.inventory = this.inventory.filter(item => item.count > 0);
this.callbacks.onInventoryUpdate?.(this.inventory);

// ❌ 错误：splice 就地修改，数组引用不变，React 不重新渲染
const index = this.inventory.findIndex(item => item.count === 0);
this.inventory.splice(index, 1);
this.callbacks.onInventoryUpdate?.(this.inventory); // React 检测不到变化！
```

### 15.3 onItemRelease 规范

当道具用完（数量归零）时，`onItemRelease()` 方法必须：

1. 使用 `filter` 创建新数组（移除 count === 0 的道具）
2. 调用 `this.callbacks.onInventoryUpdate?.(this.inventory)` 通知 UI

```typescript
// ✅ 正确：完整的道具释放流程
onItemRelease(itemType: ItemType): void {
    // 1. 从库存中移除
    this.inventory = this.inventory.filter(item => item.type !== itemType || item.count > 0);
    // 2. 通知 UI 更新
    this.callbacks.onInventoryUpdate?.(this.inventory);
}
```

### 15.4 道具栏图标消失规则

- 道具使用完最后一个后，图标必须从拾取道具栏消失
- 根因检查清单：`filter` vs `splice` | `onItemRelease` 是否调用 `onInventoryUpdate` | 新数组引用是否正确赋值

### 15.5 引擎侧集成

```typescript
// engine.ts - 绑定库存回调
this.consumableSystem = new ConsumableSystem(config, {
    onInventoryUpdate: (inventory) => {
        this.inventory = inventory;                // 同步引擎库存
        this.onInventoryUpdate?.(inventory);       // 通知 React UI
    },
});
```

## 十六、模块迁移与重构验证规则

> **核心原则：每次模块迁移后，必须验证视觉方向、伤害区域、回调闭包等关键行为与原实现一致。**

### 16.1 迁移后验证清单

| 验证项 | 说明 | 历史案例 |

```typescript
});

// ❌ 错误：直接引用，捕获构造时的值，resetGame() 后失效
this.xxxSystem = new XxxSystem(config, {
    economy: this.economy,                   // 永远指向旧对象
    roaches: this.roaches,                   // 永远指向旧数组
});
```

### 16.3 迁移标准流程

```
步骤 1 ──→ 步骤 2 ──→ 步骤 3 ──→ 步骤 4 ──→ 步骤 5
创建模块   集成引擎   替换调用   清理旧代码  验证
```

|:---:|------|------|
| 1 | 创建模块文件，实现完整逻辑 | `XxxSystem.ts` |
| 2 | 在 engine.ts 构造函数中实例化，注入回调 | 构造函数 + update() + reset() |

### 17.5 屏幕分辨率适配（Fixed Width）

> **核心原则：设计宽度固定为 540，高度由设备宽高比动态计算，背景图 Cover 裁切，消除长屏设备黑边。**

#### 适配公式

```
scale = 屏幕物理宽度 / 540
画布逻辑宽 = 540（始终不变）
画布逻辑高 = 屏幕物理高度 / scale（随设备变化）
```

#### Engine 实现

```typescript
// resize() 中使用 Fixed Width 公式
resize(rect: { width: number; height: number }) {
    const dpr = Math.min(window.devicePixelRatio || 1, 2);
    this.scale = rect.width / 540;  // ← 固定宽度缩放，不再用 Math.min
    this.width = 540;                // ← 逻辑宽度永远不变
    this.height = Math.floor(rect.height / this.scale);  // ← 高度动态计算
    this.canvas.width = 540 * dpr;
    this.canvas.height = this.height * dpr;
    ctx.setTransform(this.scale * dpr, 0, 0, this.scale * dpr, 0, 0);
}
```

#### 高度比（用于 Y 坐标缩放）

```typescript
// 当画布高度不等于 960 时，Y 坐标需等比缩放
get heightRatio(): number {
    return this.height / 960;  // 960 为设计基准高度
}
```

#### 场景地面边界缩放

```typescript
// 地面边界 Y 坐标需乘以 heightRatio
getScaledGroundBounds(): SceneGroundBounds {
    const ratio = this.heightRatio;
    // 对每个多边形的 Y 坐标缩放
    return { far: near * ratio, near: near * ratio, ... };
}
```

#### 背景图 Cover 裁切

```typescript
// 背景图居中裁切，超出的部分被裁剪
const scaleX = this.width / img.width;
const scaleY = this.height / img.height;
const coverScale = Math.max(scaleX, scaleY);  // ← Cover = max，而非 Contain = min
const drawW = img.width * coverScale;
const drawH = img.height * coverScale;
const offsetX = (this.width - drawW) / 2;
const offsetY = (this.height - drawH) / 2;
ctx.drawImage(img, offsetX, offsetY, drawW, drawH);
```

## 十九、成就解锁动画规则

> **核心原则：新解锁成就在进入成就界面时显示为灰色锁定状态，通过遮罩层依次高亮并播放解锁动画（锁→对钩、灰色→彩色），樟叔对话框跟随当前卡片移动，点击推进到下一个。**

### 19.1 动画数据流

```
关卡内成就解锁 ──→ newlyUnlockedIds.add(ach.id) ──→ 累积到队列
                  unclaimedRewards.add(ach.id)       （战斗中不显示浮动文字）
                        │
            打开成就界面 ──→ getPendingAnimations() + getUnclaimedAchievements()
                        │     ↓ 合并去重 → mergedAnimations
                        │     ↓ 创建快照队列（queueSnapshotRef，避免后续收缩导致索引错位）
                        ▼
              800ms 延迟 ──→ 遮罩层出现（bg-black/60 z-40）
                        │    卡片克隆浮层（z-50）渲染在当前成就卡片上方
                        │    初始状态：灰色 + 🔒（effectiveUnlocked = false）
                        ▼
              400ms 后 ──→ 解锁动画：锁旋转 -90°→0°、灰色→彩色渐变、金色边框发光
                        │    樟叔对话框弹入（卡片下方，跟随卡片位置）
                        ▼
              用户点击遮罩/对话框 ──→ onClaimReward(id) 发放金币
                        │            onAnimationComplete(id) 标记已播
                        │            highlightedIds 持久高亮
                        │            下一个成就自动滚动到屏幕中央
                        ▼
              最后一个成就点击 ──→ onAllAnimationsComplete()
                        │          遮罩消失，所有卡片保持彩色高亮
                        │
            关闭成就界面 ──→ clearAnimationQueue()
                        │
            新游戏开始 ──→ reset() → newlyUnlockedIds.clear()
```

### 19.2 AchievementSystem 新增接口

| 方法 | 签名 | 调用时机 |
|------|------|------|
| `getPendingAnimations()` | `() => AchievementData[]` | 打开成就界面时，获取待播放动画的成就列表 |
| `getUnclaimedAchievements()` | `() => AchievementData[]` | 打开成就界面时，获取未领取奖励的成就列表 |
| `claimReward(id)` | `(id: string) => number` | 动画播放时，领取单个成就的金币奖励并清理 `unclaimedRewards` |
| `markAnimationPlayed(id)` | `(id: string) => void` | 单个动画播放完成，从 `newlyUnlockedIds` 移除 |
| `clearAnimationQueue()` | `() => void` | 关闭成就界面时，清空所有动画标记 |

### 19.3 关键交互设计

**三层 z-index 结构**：

| 层 | z-index | 内容 | 说明 |
|----|:---:|------|------|
| 遮罩层 | 40 | `bg-black/60` 半透明遮罩 | 点击推进到下一个成就 |
| 卡片克隆浮层 | 50 | 当前成就卡片内容复制 | 灰色→彩色解锁动画，`pointer-events: none` |
| 樟叔对话框 | 50 | 头像 + 气泡文字 | 显示在卡片下方，`getBoundingClientRect()` 跟随卡片位置 |

**卡片状态控制**：

```
effectiveUnlocked = ach.unlocked AND (不是新解锁 OR 已被高亮)
```

- 新解锁的成就在高亮前显示为灰色锁定（`effectiveUnlocked = false`），即使引擎中 `unlocked = true`
- `highlightedIds` 与 `dialogPhase` 同帧更新（400ms 后），确保卡片列表和浮层克隆同步过渡
- 已解锁完毕的成就保持持久金色边框高亮（`border-yellow-400/50`）

**动画队列快照**：

```typescript
// 使用快照队列避免 onClaimReward 收缩 mergedAnimations 导致索引错位
const queueSnapshotRef = useRef<AchievementData[]>([]);
if (hasAnimations && queueSnapshotRef.current.length === 0) {
  queueSnapshotRef.current = [...mergedAnimations];
}
const currentAnim = queueSnapshotRef.current[animIndex];
```

**问题**：`onClaimReward` 移除成就后 `mergedAnimations` 动态收缩（如 [A,B,C]→[B,C]），`animIndex` 已递增到 1，导致 `mergedAnimations[1]` 指向 C 而非 B。

**解决**：在首次进入动画时冻结 `mergedAnimations` 快照，后续始终从快照中取 `currentAnim`，不受状态变化影响。

### 19.4 樟叔对话框

**文案管理**：樟叔对话框文字集中在 `achievements.ts` 的 `ACHIEVEMENT_DIALOG_TEXT` 中：

| 字段 | 用途 | 示例值 |
|------|------|--------|
| `unlockTitle` | 解锁标题 | `🎉 恭喜！解锁成就` |
| `namePrefix` / `nameSuffix` | 成就名称括号 | `「」` |
| `rewardTemplate` | 金币奖励描述 | `💰 奖励 ¥xxx 已存入账户` |
| `clickToContinue` | 推进提示 | `点击继续 ▸` |
| `clickToFinish` | 完成提示 | `点击完成 ▸` |
| `progressIndicator` | 进度指示器 | `1/3` |

**位置跟随**：对话框通过 `getBoundingClientRect()` 获取当前卡片位置，实时跟随卡片移动（`transition: top 0.35s`）。

### 19.5 战斗中不显示浮动文字

成就解锁时不再在战斗画面中显示浮动文字，统一在成就界面中展示。`AchievementSystem.grantAchievementReward()` 仅标记 `unclaimedRewards`，不调用 `onAddFloatingText`。

### 19.6 成就持久化规则

**关键约束**：`AchievementSystem.reset()` 仅重置单局数据（`newlyUnlockedIds` 动画队列 + `economyStats` 单局统计），**不得重置成就解锁状态**。成就解锁状态属于持久化数据，通过 `SaveSystem` 管理，在每局开始时应保留。

```typescript

}
```

## 二十、全局 ID 管理规则

> **核心原则：全局 ID 计数器由 engine.ts 统一管理，模块通过回调注入获取 ID，禁止模块级独立计数器。**

### 20.1 问题背景

在 `RoachAISystem.ts` 模块迁移后，模块和引擎各自维护了独立的 `nextId` 变量，两者都从 1 开始计数，导致同一游戏中出现重复 ID。重复 ID 会导致渲染错误、状态冲突和难以追踪的 Bug。

### 20.2 正确做法

**✅ 引擎侧：通过回调注入 ID 生成器**

```typescript
// engine.ts - 构造函数中注入 ID 生成器
this.roachAISystem = new RoachAISystem({
    // ... 其他配置
    getNextId: () => nextId++,  // 回调注入，所有模块共享同一个计数器
});
```

**✅ 模块侧：定义回调接口，通过回调获取 ID**

```typescript
// RoachAISystem.ts - Config 接口中定义
export interface RoachAISystemConfig {
    /** 获取下一个蟑螂 ID（回调注入，避免多模块独立计数器） */
    getNextId: () => number;
    // ...
}

// 模块中使用
const roach: Roach = {
    ...this.createRoach(spawnX, spawnY),
    id: this.cfg.getNextId(),  // 通过回调获取，而非模块级变量
};
```

**❌ 错误做法：模块级独立计数器**

```typescript
// ❌ 禁止：模块文件顶层定义 nextId 变量
let nextId = 1;  // 与 engine.ts 的 nextId 冲突！

// ❌ 禁止：模块内直接使用模块级变量
const roach = { id: nextId++ };  // 可能与引擎的 ID 重复
```

### 20.3 检查清单

- [ ] 所有模块的 ID 生成必须通过回调注入（`getNextId: () => number`）
- [ ] 模块文件中不得存在模块级 `nextId` / `nextBossId` 等独立计数器变量
- [ ] 引擎侧的 `nextId++` 是唯一的 ID 递增点
- [ ] 新增模块如果需要生成 ID，必须定义 `getNextId` 回调而非自行维护计数器

## 二十一、fireZones 生命周期管理规则

> **核心原则：`fireZones` 数组同时包含每帧武器火焰区域（`maxLife = 0.5`）和持久火焰区域（`maxLife ≥ 4`），清理时必须用 `filter` 区分，不能全量清空。**

### 21.1 问题背景

`checkCollisions()` 中曾使用 `this.fireZones = []` 清空所有火焰区域，导致燃烧瓶等投掷物创建的持久火焰区域（`maxLife = 5`）被立即清除，5 秒持续时间缩水为 1-2 帧，伤害大幅降低。

### 21.2 火焰区域类型区分

| 类型 | `maxLife` 值 | 来源 | 清理方式 |
|------|:---:|------|------|
| 每帧武器火焰 | `0.5`（`BALANCE_CONFIG.weaponDamage.fireZoneMaxLife`） | 火焰喷射器每帧创建 | 每帧清除 |
| 投掷物持久火焰 | `4-6`（`BALANCE_CONFIG.weaponDamage.fireZoneLife`） | 燃烧瓶、毒雾爆炸 | 保留至生命周期结束 |

### 21.3 正确做法

**✅ 使用 `filter` 按 `maxLife` 阈值区分**

```typescript
// engine.ts - checkCollisions()
// 保留持久火焰区域（maxLife ≥ 1），仅清除每帧武器火焰区域（maxLife = 0.5）
this.fireZones = this.fireZones.filter(z => z.maxLife >= 1);
```

**❌ 错误做法：全量清空**

```typescript
// ❌ 禁止：清空所有火焰区域，破坏持久火焰
this.fireZones = [];
```

### 21.4 三重清扫机制

火焰区域的完整生命周期由三个清扫点协同管理：

| 清扫点 | 位置 | 操作 | 清理对象 |
|--------|------|------|------|
| `ParticleSystem.updateFireZones()` | `ParticleSystem.ts` | `life -= dt`，移除 `life ≤ 0` 的火焰区域 | 生命周期自然结束的火焰区域 |
| `checkCollisions()` | `engine.ts` | `filter(z => z.maxLife >= 1)` | 每帧武器火焰区域（`maxLife = 0.5`） |
| `ParticleSystem` 数量上限 | `ParticleSystem.ts` | `splice(0, length - maxZones)` | 超过最大数量限制的最旧火焰区域 |

### 21.5 检查清单

- [ ] 火焰区域清理使用 `filter` 而非 `= []`
- [ ] `maxLife` 阈值正确区分每帧武器火焰和持久火焰
- [ ] 新增火焰区域类型时，设置正确的 `maxLife` 值（`≥ 1` 表示持久，`< 1` 表示每帧清除）
- [ ] 三重清扫机制（ParticleSystem 生命周期 / engine 每帧清除 / 数量上限）互相不冲突

## 二十二、图片资源加载规则

> **核心原则：`imagesLoaded` 标志必须在所有图片加载完成后设置，每张图片必须添加 `onerror` 处理，加载失败不阻塞游戏启动。**

### 22.1 问题背景

`loadImages()` 在启动 50+ 个异步图片加载后立即设置 `this.imagesLoaded = true`，此时所有图片仍为 `null`。`render()` 中多处依赖此标志，可能导致首帧渲染时图片缺失。同时，图片加载没有 `onerror` 处理，404 或网络错误时图片属性永远为 `null`。

### 22.2 正确做法

**✅ 使用 `Promise.all` 等待所有图片加载**

```typescript
loadImages() {
    const loadPromises: Promise<void>[] = [];
    
    const load = (src: string, setter: (img: HTMLImageElement) => void) => {
        const promise = new Promise<void>((resolve) => {
            const img = new Image();
            img.onload = () => { setter(img); resolve(); };
            img.onerror = () => {
                console.warn(`[Engine] Failed to load image: ${src}`);
                resolve();  // 加载失败不阻塞，继续加载其他资源
            };
            img.src = src;
        });
        loadPromises.push(promise);
    };
    
    // 加载所有图片
    load('/assets/roach.png', (img) => { this.roachImg = img; });
    load('/assets/boss.png', (img) => { this.bossImg = img; });
    // ... 更多图片
    
    // 所有图片加载完成后设置标志
    Promise.all(loadPromises).then(() => {
        this.imagesLoaded = true;
    }).catch(() => {
        this.imagesLoaded = true;  // 即使部分失败也允许渲染
    });
}
```

**❌ 错误做法**

```typescript
// ❌ 禁止：异步加载完成前设置标志
loadImages() {
    load('/assets/roach.png', (img) => { this.roachImg = img; });
    load('/assets/boss.png', (img) => { this.bossImg = img; });
    this.imagesLoaded = true;  // 此时所有图片仍为 null！
}

// ❌ 禁止：没有 onerror 处理
const img = new Image();
img.onload = () => { setter(img); };
// 缺少 img.onerror —— 404 时 setter 永远不会被调用
img.src = src;
```

### 22.3 检查清单

- [ ] `imagesLoaded` 在 `Promise.all(loadPromises).then()` 中设置，而非同步设置
- [ ] 每张图片的 `load()` 调用都添加了 `onerror` 回调
- [ ] `onerror` 中调用 `resolve()` 确保不阻塞其他图片加载
- [ ] 渲染代码中所有图片使用前都检查 `if (img)` 防御空引用
- [ ] `.catch()` 兜底确保即使部分失败也允许游戏渲染

## 二十三、死亡链递归管理规则

> **核心原则：递归爆炸方法中必须正确配对 `depth++` / `depth--`，防止深度计数器失效导致指数级递归。**

### 23.1 问题背景

`suicideExplode()` 方法中，`_deathChainDepth` 计数器仅在死代码 `triggerBreachExplosion()` 中递增，`suicideExplode()` 只检查不递增。导致死亡链深度限制从未生效，可能引发指数级递归爆炸。

### 23.2 正确做法

**✅ 递归调用前后配对 `depth++` / `depth--`**

```typescript
// engine.ts - suicideExplode()
private suicideExplode(roach: Roach, particles: Particle[], roaches: Roach[]): void {
    // 深度限制检查
    if (this._deathChainDepth >= MAX_DEATH_CHAIN_DEPTH) {
        return;  // 达到最大深度，停止递归
    }
    
    // 爆炸逻辑...
    
    // 递归处理连锁爆炸
    for (const nearby of nearbyRoaches) {
        this._deathChainDepth++;  // ✅ 进入递归前递增
        this.suicideExplode(nearby, particles, roaches);
        this._deathChainDepth--;  // ✅ 递归返回后递减
    }
}
```

**❌ 错误做法**

```typescript
// ❌ 只检查不递增 —— 深度限制从未生效
private suicideExplode(roach: Roach, particles: Particle[], roaches: Roach[]): void {
    if (this._deathChainDepth >= MAX_DEATH_CHAIN_DEPTH) return;
    // 缺少 this._deathChainDepth++
    
    for (const nearby of nearbyRoaches) {
        this.suicideExplode(nearby, particles, roaches);  // 深度不变！
    }
}
```

### 23.3 检查清单

- [ ] 递归方法入口处检查深度上限（`>= MAX_DEPTH` 时 `return`）
- [ ] 递归调用前 `depth++`，递归返回后 `depth--`（配对使用）
- [ ] `depth` 计数器不在方法入口处重置为 0（由调用链管理）
- [ ] `MAX_DEPTH` 常量值合理（3-5），防止无限递归

## 二十四、临时武器弹药管理规则

> **核心原则：弹药消耗使用整数递减（`-= 1`），禁止浮点递减，避免浮点精度导致弹药永远不归零。**

### 24.1 问题背景

临时武器（雷达激光、电蚊拍等）弹药使用浮点递减（`weaponAmmo[key] -= deltaTime * 3`），而燃烧瓶使用整数递减（`molotovCount--`）。浮点精度可能导致 `0.0000000001` 永远不归零，弹药检查 `<= 0` 永远不触发，武器无法正常过期。

### 24.2 正确做法

**✅ 统一使用整数递减**

```typescript
// engine.ts - 临时武器弹药消耗
const ammoKey = `${weaponType}Ammo` as keyof PlayerWeaponAmmo;
player.weaponAmmo[ammoKey] = Math.max(0, (player.weaponAmmo[ammoKey] || 0) - 1);
```

**❌ 错误做法**

```typescript
// ❌ 禁止：浮点递减
player.weaponAmmo[ammoKey] -= deltaTime * 3;  // 0.016 * 3 = 0.048，精度问题

// ❌ 禁止：混合使用整数和浮点递减
this.molotovCount--;                        // 整数递减
player.weaponAmmo.radarAmmo -= deltaTime * 3;  // 浮点递减 —— 不一致！
```

### 24.3 检查清单

- [ ] 所有弹药消耗使用整数递减（`-= 1` 或 `--`）
- [ ] 递减后使用 `Math.max(0, value)` 防止负数
- [ ] 同一系统中所有弹药使用相同的递减方式（不要混用整数和浮点）
- [ ] 弹药检查条件使用 `<= 0` 而非 `=== 0`（防御性编程）
