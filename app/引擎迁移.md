## 一、迁移策略

### 1.1 核心思路：渐进式提取（Gradual Extraction）

不同于传统的"重写新引擎再切换"，本项目采用**从现有 engine.ts 逐步提取**的策略：

```
engine.ts (原始单体文件, ~9700行)
    │
    ├── 提取 SaveSystem ──→ engine/save/SaveSystem.ts
    ├── 提取 EconomyManager ──→ engine/economy/EconomyManager.ts
    ├── 提取 AchievementSystem ──→ engine/achievement/AchievementSystem.ts
    ├── ... (逐个提取)
    │    └── engine.ts (持续缩小, 当前 ~3120 行)
```

**优点**：
- 每一步改动小，风险可控
- 每次迁移后立即编译+测试，问题早发现
- 不需要维护两套引擎并行运行
- 旧代码逐步删除，不留冗余

### 1.2 迁移七步法

每个模块的提取遵循固定流程：

| 步骤 | 操作 | 说明 |
|:---:|------|------|
| 1 | 创建/更新模块类 | 编写独立模块文件，定义 Config 接口和回调 |
| 2 | 在 engine.ts 中导入 | `import { XxxSystem } from './engine/xxx/XxxSystem'` |
| 3 | 构造函数中实例化 | 传入回调函数，实现模块↔引擎通信 |
| 4 | 替换方法调用为委托 | 将 `this.xxx()` 替换为 `this.xxxSystem!.xxx()` |
| 5 | 移除旧属性和方法 | 删除 engine.ts 中已提取的属性和方法定义 |
| 6 | 更新 resetGame() | 确保重置时模块状态正确恢复 |
| 7 | 编译+构建验证 | 必须通过 `npx tsc --noEmit` 和 `npx vite build` |

### 1.3 模块↔引擎通信机制：回调（Callbacks）

模块通过构造函数接收回调函数，实现与引擎的解耦通信：

```typescript
// 引擎端 - 注入回调
this.poisonSystem = new PoisonSystem({
  onAddFloatingText: (x, y, text, color) => { this.addFloatingText(x, y, text, color); },
  onScreenShake: (amount) => { this.screenShake = amount; },
});

// 模块端 - 调用回调
this.config.onAddFloatingText?.(x, y - 20, '毒雾!', '#a78bfa');
```

常用回调：`onAddFloatingText`、`onPlaySound`、`onVibrate`、`onScreenShake`、`onAddParticle`、`onEconomyUpdate`、`onPlayerUpdate`、`onDefenseUpdate` 等。

### 1.4 关键约束

- **每次迁移后必须通过编译验证**：`npx tsc --noEmit` + `npx vite build`
- **回调闭包陷阱**：ConsumableSystem 等模块的回调必须用箭头函数包装，运行时动态读取最新值，避免捕获 `undefined`
- **`replace_all` 安全**：仅当目标字符串是完整标识符、不包含其他标识符作为子串时才能使用
- **`onDefenseUpdate` 回调**：必须先更新引擎内部状态（`this.defenseHp`、`this.maxDefenseHp`），再通知 UI

## 七、UI 覆盖层架构优化

### 8.1 画布覆盖层分层架构（GameCanvas.tsx）

`GameCanvas.tsx` 中采用两层覆盖层设计，解决 UI 元素定位和交互穿透问题：

```
GameCanvas (外层容器)
├── <canvas> 游戏画面
├── gameplay-overlay (z-10, 动态匹配画布边界)
│   ├── 视觉特效层（Power Boost 光效、防线危急警告）
│   ├── CountdownOverlay（波次倒计时）
│   ├── GameplayTutorialOverlay（新手引导遮罩）
│   └── GameHUD（火力槽、道具栏、暂停按钮）
└── full-screen overlay (z-20, 全屏)
    └── 菜单 / 暂停 / 结算 / 商店 / 天赋 / 成就 / 图鉴
```

**关键设计决策**：

| 层级 | z-index | 定位方式 | 用途 |
|------|:---:|------|------|
| gameplay-overlay | 10 | `absolute`，通过 `canvasBounds`（ResizeObserver）动态匹配画布位置和尺寸 | 战斗内 UI，跟随画布 |
| full-screen overlay | 20 | `absolute inset-0`，填充 `#game-container` | 全屏 UI，独立于画布 |
| 教程遮罩 | 200 | `absolute inset-0`，在 gameplay-overlay 内 | 最高层级，覆盖战斗 UI |

**交互穿透控制**：full-screen overlay 使用动态 `pointer-events-none`，仅在有可见 UI 内容时启用交互，其余时间事件穿透到 gameplay-overlay。

### 8.2 背景图统一化

四个全屏界面统一使用 `achieve_bg.jpg` 作为背景，采用 `fixed` 定位确保背景不随内容滚动：

| 界面 | 文件 | 修改内容 |
|------|------|------|
| 成就系统 | `AchievementsScreen.tsx` | 背景图 + 暗色遮罩从 `absolute` → `fixed` |
| 道具商店 | `ShopScreen.tsx` | 新增背景图 + 暗色遮罩（`fixed`） |
| 天赋树 | `TalentTreeScreen.tsx` | 纯黑背景 → 背景图 + 暗色遮罩（`fixed`） |
| 蟑螂图鉴 | `EncyclopediaScreen.tsx` | 渐变背景 → 背景图 + 暗色遮罩（`fixed`） |

**`absolute` vs `fixed` 定位**：
- `absolute`：相对于最近的定位祖先，当父容器可滚动时，背景随内容一起移动
- `fixed`：相对于浏览器视口，始终固定在屏幕上，不随滚动移动

### 8.3 响应式适配

**道具商店**（`ShopScreen.tsx`）：
- 高度适配屏幕：`max-h-[90vh]`（最大高度 = 视口高度的 90%）
- 宽度约束：`max-w-md`（最大 448px）+ `w-full`（小屏填满）
- 内部内容通过 `overflow-y-auto` 滚动

**天赋界面**（`TalentTreeScreen.tsx`）：

- 避免在大屏上 UI 元素散落到屏幕边缘

**重置确认对话框**（`GameMenu.tsx`）：
- 遮罩层从 `absolute` → `fixed`，确保在任何屏幕尺寸下完整覆盖视口

### 8.4 教程遮罩自适应（v2.12.0 升级为混合定位）

`GameplayTutorialOverlay` 采用**混合定位策略**：

**Canvas 绘制区域**（火焰控制区、战斗区域、防线）使用百分比定位：
```typescript
// 高亮区域定义（百分比，独立于分辨率）
highlightArea: { x: 0.34, y: 0.05, width: 0.32, height: 0.04 }

// 运行时换算（canvasBounds 来自 ResizeObserver）
left: highlight.x * canvasBounds.width
```

**HUD DOM 元素**（防线血条、热力条、燃气条、道具栏、武器栏）使用 `getBoundingClientRect()` 精确定位：
```typescript
// 通过 ref 回调注册 DOM 元素
onRegisterTutorialElement?.(id, el);

// 教程组件读取真实 viewport 坐标
const rect = hudRefs.current[highlightRef].getBoundingClientRect();
```

**高亮区域调整器**：通过 `highlightAdjust` 回调在原始 DOM 矩形基础上缩放/偏移：
```typescript
highlightAdjust: (rect) => {
  // 以右下角为基准，向上扩大4倍
  return { left: rect.right - rect.width, top: rect.bottom - rect.height * 4, ... };
};
```

**数据流**：
```
GameHUD → onRegisterTutorialElement → GameCanvas.tutorialHudRefs → GameplayTutorialOverlay.hudRefs
                                   ↓
ResizeObserver → canvasBounds → GameplayTutorialOverlay →
                                   ↓
  → getBoundingClientRect() (DOM 元素) 或 百分比 × canvasBounds (画布区域)
  → highlightAdjust (可选调整)
  → fixed inset-0 遮罩 + 四片聚光灯
```

**对比旧方案**（纯百分比）：
- 旧方案：所有高亮区域硬编码百分比 → 手机端 HUD 元素位置与百分比不匹配 → 偏移
- 新方案：HUD 元素用真实 DOM 坐标 → 100% 精确，不受屏幕尺寸影响

## 十、战斗界面移动端视口适配

### 10.1 动态视口高度（dvh）

手机浏览器地址栏会动态显示/隐藏，导致 `100vh`（CSS 静态视口高度）不等于用户实际可见区域。

**解决方案**：将战斗界面容器高度从 `h-screen`（100vh）改为 `h-dvh`（100dvh，dynamic viewport height）：

```tsx
// 修改前：地址栏显示时，底部内容被裁切
<div className="relative w-screen h-screen ...">

// 修改后：地址栏变化时，容器高度实时跟随可见区域
<div className="relative w-screen h-dvh ...">
```

| 单位 | 含义 | 地址栏显示时 | 地址栏隐藏时 |
|------|------|:---:|:---:|
| `100vh` | 静态视口高度 | 包含地址栏高度 → 底部裁切 | = 可见区域 |
| `100dvh` | 动态视口高度 | = 可见区域（不含地址栏） | = 可见区域 |

**影响范围**：`GameCanvas.tsx`（战斗场景容器）、`AchievementsScreen.tsx`、`EncyclopediaScreen.tsx`。

### 10.2 覆盖层 fixed 定位

战斗界面覆盖层（gameplay-overlay）从 `absolute` 改为 `fixed` 定位，确保 HUD 元素始终相对于**屏幕视口**定位，而非相对于可能在 `100vh` 容器中偏移的画布：

```tsx
// 修改前：absolute 跟随画布位置，地址栏变化时偏移
<div className="absolute z-10" style={{ left: canvasBounds.left, top: canvasBounds.top, ... }}>

// 修改后：fixed 相对于视口，不受地址栏影响
<div className="fixed z-10" style={{ left: canvasBounds.left, top: canvasBounds.top, ... }}>
```

### 10.3 画布 Contain 等比缩放

#### 10.8.2 橡皮筋效果（页面拖动回弹）

**问题**：iOS Safari 默认的 overscroll 行为，用户在游戏画面上拖动时整个页面会跟随移动并回弹，破坏游戏体验。

**解决方案（两层防护）**：

| 层级 | 方案 | 实现位置 |
|:---:|------|------|
| CSS | `body { overscroll-behavior: none }` | `index.css` |
| JS | `touchmove` 事件对游戏容器内所有触摸调用 `preventDefault()` | `GameCanvas.tsx` |

**关键注意事项**：

- **`touchstart` 只能拦截 canvas 元素**，不能拦截整个游戏容器。因为 `touchstart` 的 `preventDefault()` 会阻止浏览器生成后续的 `click` 事件，导致 UI 按钮（标题画面"开始"、武器选择器、消耗品按钮等）无法点击。
- **`touchmove` 可以拦截整个游戏容器**，因为 `touchmove` 的 `preventDefault()` 不会阻止 `click` 事件。

```typescript
// GameCanvas.tsx — 触摸事件处理
const handleGlobalTouchStart = (e: TouchEvent) => {
  // ✅ 仅 canvas：保留 UI 按钮的 click 事件
  if (e.target === canvasRef.current) {
    e.preventDefault();
  }
  // ... 游戏逻辑
};

const handleGlobalTouchMove = (e: TouchEvent) => {
  // ✅ 全容器：防止橡皮筋回弹，不影响 click
  if (gameContainerRef.current?.contains(e.target as Node)) {
    e.preventDefault();
  }
  // ... 游戏逻辑
};
```

**错误案例**：曾将 `touchstart` 的 `preventDefault()` 范围扩大到整个游戏容器，导致标题画面"开始"按钮点击无效，手机端无法进入主菜单。

**不推荐但已排除的方案**：

| 方案 | 问题 |
|------|------|
| `html, body { position: fixed }` | 移动端视口高度计算异常，React 渲染内容被裁剪，表现为白屏 |
| `html, body { overflow: hidden }` | 与 `position: fixed` 组合使用时加剧上述问题 |
| `#root { position: fixed }` | 破坏 React 挂载点的正常文档流 |

### 10.9 Economy 引用同步修复

**问题**：消灭蟑螂后金币不增长（UI 始终显示 0）。

**根因**：`RoachAISystem`（蟑螂 AI 模块）持有的 `economy` 引用与引擎的 `this.economy` 是两个不同的对象，击杀奖励加到了旧对象上，UI 显示的是新对象。

```typescript
// engine.ts - resetGame()
this.economy = this.createEconomy(initialMoney); // ① 创建新 economy 对象
this.roachAISystem?.updateConfig({
  roaches: this.roaches,
  particles: this.particles,
  fireWalls: this.fireWalls,
  armorShieldCache: this.armorShieldCache,
  // ❌ 缺少 economy: this.economy —— RoachAISystem 仍持有旧引用
});
```

**引用过期链路**：

```
resetGame() 创建新 economy ──→ engine.ts 的 this.economy 指向新对象
                                    │
    updateConfig 没有同步 economy ──┘  RoachAISystem.cfg.economy 仍指向旧对象
                                    │
    击杀蟑螂 ──→ RoachAISystem.killRoach() ──→ 旧对象.money += reward  ✅ 加了但没人看
    更新 UI ──→ onEconomyUpdate(新对象) ──→ 新对象.money = 0           ❌ 始终为 0
```

**修复（两处）**：

| 位置 | 触发场景 | 修复方式 |
|------|------|------|
| `resetGame()` → `updateConfig` | 新游戏 / 重新开始 / 下一关 | 新增 `economy: this.economy` |
| `setEconomy` 回调（ConsumableSystem） | 购买消耗品时创建新对象 | 新增 `this.roachAISystem?.updateConfig({ economy: e })` |

**关键教训**：当引擎通过 `resetGame()` 重建数据对象时，所有持有这些对象引用的模块都必须通过 `updateConfig()` 同步。`ConsumableSystem` 不受影响因为它使用 `getEconomy: () => this.economy`（getter 函数，每次调用返回最新引用），而 `RoachAISystem` 使用 `economy: this.economy`（构造时捕获的固定引用）。

### 10.14 变异蟑螂多杀修复

**问题**：医院场景中，当两个或多个变异蟑螂在同一帧被杀死时，只有最后一只触发"胚胎暴走"（变异生成小蟑螂），其他变异蟑螂的变异丢失。

**根因**：`RoachAISystem.ts` 中 `forceEmbryoBurst()` 使用**全局单例状态变量**追踪变异动画：

```typescript
// 单例状态（同一时间只能追踪一个变异）
mutantTransformActive: boolean = false;
mutantTransformFrame: number = 0;
mutantTransformTimer: number = 0;
mutantTransformX: number = 0;
mutantTransformY: number = 0;
_embryoSpawnTypes: RoachType[] = [];
```

当两个变异蟑螂在同一帧死亡时，第二个 `forceEmbryoBurst()` 调用**覆盖**第一个的状态。动画完成后，`spawnEmbryoRoaches()` 只生成第二个变异的数据。

**修复**：将变异变换状态从全局单例**迁移到每只蟑螂的 `Roach` 对象上**：

| 文件 | 改动 |
|------|------|
| `types.ts` | 新增 `transformFrame`、`transformSpawnTypes` 字段到 `Roach` 接口 |
| `RoachAISystem.ts` | 删除 5 个单例状态变量；`forceEmbryoBurst(r)` 写入 `r.transformFrame`/`r.transformSpawnTypes`；`update()` 遍历所有 DEAD MUTANT roach 独立更新变换动画；`spawnEmbryoRoaches(r)` 接受 roach 参数 |
| `engine.ts` | 移除 `mutantTransformActive`/`mutantTransformFrame` 渲染传参 |
| `RoachRenderer.ts` | 从 `r.transformFrame` 读取变换帧，移除 config 中的单例字段 |

**设计要点**：每只变异蟑螂独立维护自己的变换状态（帧、计时器、生成类型），多个变异可同时进行 7 帧序列动画，互不干扰。

### 10.15 定时自爆蟑螂炸弹行为改进

**问题**：定时自爆蟑螂在 breach 系统（突破阶段）中，蹲下 3 秒后自身爆炸（`triggerBreachExplosion`），没有安放炸弹也没有变身为大蟑螂。旧代码在 `crouching` 阶段让蟑螂蹲下倒计时，`exploding` 阶段触发自身爆炸，`residue` 阶段死亡残留。

**阶段变更**：

### 10.16 TEXT_CONFIG 导入遗漏修复（道具图标不消失）

**问题**：风扇、杀虫喷雾、散弹枪三个道具使用完最后一个后图标不消失，其它道具正常。

**根因**：在文本集中化迁移（TEXT_CONFIG）时，三个子系统文件使用了 `TEXT_CONFIG` 但遗漏了 `import { TEXT_CONFIG } from '../../data'`，导致激活时抛出 `ReferenceError: TEXT_CONFIG is not defined`：

4. 道具图标留在道具栏中

### 10.17 金币体系重构（pendingRewards / victoryGoldReward）

**问题**：关卡内击杀蟑螂获得的金币不显示在 HUD 上，且成就奖励直接加到总金币池而非关卡金币。

**重构内容**：

**新增属性**：

| 属性 | 位置 | 说明 |
|------|------|------|
| `pendingRewards` | `engine.ts` | 关卡内累计金币，HUD 实时显示，初始 0 |
| `victoryGoldReward` | `engine.ts` | 胜利时从 `pendingRewards` 拷贝，供结算界面动画展示 |
| `onPendingRewardUpdate` | `engine.ts` 回调 | 通知 React 更新 HUD 金币显示 |
| `settleVictoryGold()` | `engine.ts` 方法 | 结算界面动画完成后实际发放金币 |

**金币流转**：

```
击杀/成就/奖励 ──→ pendingRewards ──→ GameHUD 实时显示 ¥{pendingRewards}
                        │
            胜利 ──→ victoryGoldReward ──→ 结算界面动画 ──→ settleVictoryGold()
                        │                                      │
                        │                                      ▼
                        │                              economy.money += victoryGoldReward
                        │
          失败/退出 ──→ pendingRewards = 0（不发放）
```

**关键修改**：

### 10.18 引擎审查 Bug 修复（2026-07-29）

对 `engine.ts`、`RoachAISystem.ts`、`ParticleSystem.ts` 进行了系统性代码审查，发现并修复 8 个 Bug：

#### P0-1: 全局 ID 计数器双重管理

**问题**：`engine.ts`（L147）和 `RoachAISystem.ts`（L86）各自维护独立的模块级 `nextId` 变量，两者都从 1 开始计数，导致同一游戏中出现重复 ID。

**修复**：
- 移除 `RoachAISystem.ts` 中的模块级 `nextId`/`nextBossId` 变量及 `getNextId`/`setNextId` 导出函数
- 在 `RoachAISystemConfig` 接口中新增 `getNextId: () => number` 回调
- `engine.ts` 中注入 `getNextId: () => nextId++` 回调
- `RoachAISystem.ts` 中 `forceEmbryoBurst()` 的 `id: nextId++` → `id: this.cfg.getNextId()`

**涉及文件**：`RoachAISystem.ts`、`engine.ts`

#### P0-2: fireZones 生命周期管理

**问题**：`checkCollisions()` 中 `this.fireZones = []` 清空了所有火焰区域，包括燃烧瓶等投掷物创建的持久火焰区域（`maxLife=5`）。持久火焰区域每帧被清空，5 秒持续时间缩水为 1-2 帧，伤害大幅降低。

**修复**：`checkCollisions()` 中改为 `this.fireZones = this.fireZones.filter(z => z.maxLife >= 1)`，保留持久火焰区域（`maxLife ≥ 1`），仅清除每帧武器火焰区域（`maxLife = 0.5`）。

**设计要点**：每帧武器火焰区域（`fireZoneMaxLife = 0.5`）和投掷物持久火焰区域（`fireZoneLife = 4-6`）共享同一个 `fireZones` 数组。通过 `maxLife` 阈值 ≥ 1 区分两种类型。

**涉及文件**：`engine.ts`

#### P1-1: imagesLoaded 标志设置时机

**问题**：`loadImages()` 在启动 50+ 个异步图片加载后立即设置 `this.imagesLoaded = true`，此时所有图片仍为 `null`。`render()` 中多处依赖此标志，可能导致首帧渲染时图片缺失。

**修复**：
- `load()` 内部函数改为返回 Promise，收集所有 `loadPromises`
- 使用 `Promise.all(loadPromises)` 等待所有图片加载完成后设置 `this.imagesLoaded = true`
- `.catch()` 兜底确保即使部分失败也允许渲染

**涉及文件**：`engine.ts`

#### P1-2: 死亡链深度计数修正

**问题**：`_deathChainDepth` 计数器仅在 `triggerBreachExplosion()`（死代码，从未被调用）中递增，`suicideExplode()` 中只检查不递增。导致死亡链深度限制从未生效，可能引发指数级递归爆炸。

**修复**：
- 在 `suicideExplode()` 的递归调用处添加 `this._deathChainDepth++` / `this._deathChainDepth--` 配对
- 移除 `killRoach()` 入口处的 `_deathChainDepth = 0` 重置（由 `suicideExplode` 管理）
- `MAX_DEATH_CHAIN_DEPTH = 3` 现在实际允许 3 层递归

**涉及文件**：`engine.ts`

#### P1-3: 临时武器弹药消耗逻辑不一致

**问题**：临时武器弹药使用浮点递减（`weaponAmmo[key] -= deltaTime * 3`），而燃烧瓶使用整数递减（`molotovCount--`）。浮点精度可能导致弹药永远不归零。

**修复**：统一为整数递减 `weaponAmmo[ammoKey] = Math.max(0, (p.weaponAmmo[ammoKey] || 0) - 1)`

**涉及文件**：`engine.ts`

#### P2-1: 图片加载无错误处理

**问题**：`load()` 函数只设置 `img.onload`，没有 `img.onerror`。404 或网络错误时图片属性永远为 `null`，UI 渲染处虽用 `if (img)` 防御，但无降级提示。

**修复**：添加 `img.onerror` 回调，`console.warn` 日志并 `resolve()` 继续加载其他资源。

**涉及文件**：`engine.ts`

#### P2-2: 虫卵系统残留代码清理

**问题**：虫卵系统已完全移除，但 `hospitalTotalEggPods`、`hospitalDestroyedEggPods` 字段和 10 处 `[REMOVED]` 注释仍残留。

**修复**：移除 2 个无用字段，清理所有 `[REMOVED]` 注释标记。

**涉及文件**：`engine.ts`

#### P2-3: 方法命名误导

**问题**：`ParticleSystem.updateParticlesAndFloatingTexts()` 方法名仍含 "FloatingTexts"，但浮动文字已由独立的 `FloatingTextSystem` 管理。与私有方法 `updateParticles()` 存在命名冲突。

**修复**：重命名为 `syncParticleArrays()`，避免与私有方法冲突，准确反映其职责（同步外部数组到粒子系统）。

**涉及文件**：`ParticleSystem.ts`、`engine.ts`
